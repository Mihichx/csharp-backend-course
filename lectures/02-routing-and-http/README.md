# Лекция 2. Основы ASP.NET Core Web API: Маршрутизация, CRUD и протокол HTTP

На этом занятии создадим Web API на контроллерах, научимся управлять данными в памяти сервера (простой CRUD), разберем правила построения красивых маршрутов (REST) и заглянем «под капот» протокола HTTP.

## 1. GET-запросы и основы маршрутизации

Когда клиент (браузер, мобильное приложение) обращается к серверу, сервер принимает решение, какой именно метод C# нужно запустить. Этот процесс называется **маршрутизацией (Routing)**.

Маршрут — это URL-адрес ресурса. Хорошая практика (REST-подход) — называть маршруты **существительными во множественном числе**, отражающими суть данных (например, `/api/students`), а не глаголами (`/get-all-students` — это антипаттерн). Действие, которое мы хотим совершить с ресурсом, определяется типом HTTP-запроса:
- `GET` — получить
- `POST` — создать
- `PUT` — обновить целиком
- `PATCH` — обновить часть данных
- `DELETE` — удалить.

На этом занятии поработаем с GET, POST, DELETE. Начнем с GET.

### Способы передачи параметров в GET-запросах

| Способ передачи | Как выглядит в URL | Когда использовать (Best Practice) |
| :--- | :--- | :--- |
| **Строка запроса (Query parameters)** | `/api/students?search=иван` | Для **фильтрации, поиска, сортировки** или пагинации. Эти параметры почти всегда являются необязательными. |
| **Параметры маршрута (Route parameters)** | `/api/students/4` | Для **точечной идентификации** конкретного ресурса (например, по ID). Без этого параметра запрос теряет смысл. |

Пропишем в контроллере список студентов. Элементы списка — строки (модели разберем на следующей лекции). Поскольку есть только строки, с ID пока не работаем. Будем искать студентов в списке по подстроке => используем **Query-параметры**, так как фильтрация по строке поиска — это опциональное действие (если параметр пустой, мы просто отдаем всех студентов).

> [!NOTE]
> **Почему список студентов статический (`static`)?**  
> При каждом входящем HTTP-запросе ASP.NET Core создает *новый экземпляр* класса контроллера, выполняет нужный метод и уничтожает этот экземпляр. Если сделать список обычным, он будет сбрасываться до исходного состояния при каждом запросе. Ключевое слово `static` заставляет список жить в памяти сервера все время, пока приложение запущено.

### Код контроллера (`Controllers/StudentController.cs`)

```csharp
using Microsoft.AspNetCore.Mvc;

namespace WebApiLecture.Controllers;

[ApiController]
[Route("api/[controller]")] // Шаблон автоматически превратится в api/students
public class StudentsController : ControllerBase
{
    // Статический список в памяти — временная имитация базы данных
    private static readonly List<string> Students = new()
    {
        "Иван Иванов", "Мария Сидорова", "Алексей Петров", "Ирина Козлова"
    };

    // Получение всех студентов или фильтрация по имени (через Query-параметры)
    [HttpGet]
    public IActionResult Get([FromQuery] string? search)
    {
        // Если параметр поиска не передан или пуст — возвращаем весь список
        if (string.IsNullOrWhiteSpace(search))
        {
            return Ok(Students); // Статус 200 OK
        }

        // Фильтруем список (содержит подстроку без учета регистра)
        var filtered = Students
            .Where(s => s.Contains(search, StringComparison.OrdinalIgnoreCase))
            .ToList();

        return Ok(filtered); // Статус 200 OK с отфильтрованным списком
    }
}
```

### 🔍 Тестирование (`requests.http`)

```http
@host = http://localhost:5000

### Запрос 1: Получить всех студентов (без фильтрации)
GET {{host}}/api/students

### Запрос 2: Фильтрация по строке запроса (Query)
GET {{host}}/api/students?search=иван
```
*(Для выполнения запроса нажмите на зеленую стрелочку `Run` слева от строки метода в редакторе Rider).*

## 2. Изменение данных (POST, DELETE) и обработка ошибок

Для добавления и удаления данных используются HTTP-методы `POST` и `DELETE`. При проектировании этих методов важно правильно выбрать место для передачи параметров.

### Способы передачи параметров в POST-запросах
| Способ передачи | Как выглядит в URL / Запросе | Когда использовать (Best Practice) |
|---|---|---|
| Тело запроса (Request Body) | Скрыто из URL (передается внутри Body в формате JSON, Form-data и др.) | Основной способ. Для передачи всей структуры данных создаваемого объекта (например, профиль пользователя, статья блога или загружаемый файл). |
| Параметры маршрута (Route parameters) | /api/posts/42/comments | Для указания целевого или родительского ресурса, внутри которого создается новый объект (в примере: создание комментария внутри поста с ID 42). |
| Строка запроса (Query parameters) | /api/users?send_email=false | Используется редко. Подходит для флагов-модификаторов или скрытых настроек самого процесса создания ресурса. |

### Способы передачи параметров в DELETE-запросах
| Способ передачи | Как выглядит в URL / Запросе | When to use (Best Practice) |
|---|---|---|
| Параметры маршрута (Route parameters) | /api/students/4 | Основной способ. Для точечного удаления конкретного ресурса по его уникальному ID. Без этого параметра запрос обычно не имеет смысла. |
| Строка запроса (Query parameters) | /api/sessions?expired=true | Для массового или условного удаления по определенному фильтру (например, удалить все старые сессии, очистить корзину или логи за конкретную дату). |
| Тело запроса (Request Body) | Скрыто из URL (передается внутри Body) | Не рекомендуется. Архитектура многих прокси-серверов и фреймворков настроена так, что тело в DELETE просто игнорируется. Применяется в редких исключениях (например, пакетное удаление по списку из сотен ID). |

Для работы со списком студентов сделаем такой выбор.
1. **POST (Создание): Данные передаются в Теле запроса (`[FromBody]`)**  
2. **DELETE (Удаление): Данные передаются через Строку запроса (`[FromQuery]`)**  
   Поскольку ID-шников пока нет, мы не можем использовать Route-параметры. Удаляем студента по имени, передавая его через Query-параметр `?name=Иван` (как бы нашли по фильтру и удалили).

Важнейшая задача Web API — **валидация данных и отправка корректных статус-кодов**:
* `200 OK` или `201 Created` — данные успешно обработаны/созданы.
* `400 Bad Request` — ошибка со стороны клиента (например, отправлена пустая строка вместо имени).
* `404 Not Found` — запрашиваемый объект не существует на сервере (например, попытка удалить несуществующего студента).

### 💻 Дополнение кода контроллера (`StudentController.cs`)

Добавьте эти методы внутрь класса контроллера:

```csharp
    // Добавление нового студента (Имя принимается из тела запроса)
    [HttpPost]
    public IActionResult Add([FromBody] string name)
    {
        if (string.IsNullOrWhiteSpace(name))
        {
            return BadRequest("Имя студента не может быть пустым."); // Статус 400
        }

        Students.Add(name.Trim());
        return Created("", name); // Статус 201 Created
    }

    // Удаление студента (Имя принимается из строки запроса)
    [HttpDelete]
    public IActionResult Delete([FromQuery] string name)
    {
        // Ищем индекс элемента без учета регистра
        var studentIndex = Students.FindIndex(s => s.Equals(name, StringComparison.OrdinalIgnoreCase));
        
        if (studentIndex == -1)
        {
            return NotFound(\$"Студент '{name}' не найден."); // Статус 404
        }

        Students.RemoveAt(studentIndex);
        return Ok(\$"Студент '{name}' успешно удален."); // Статус 200 OK
    }
```

## 3. Анатомия HTTP-протокола

Любое взаимодействие в веб-разработке строится на протоколе **HTTP**. По сути, это простой структурированный текст. Каждое сообщение (и запрос, и ответ) состоит из **3 обязательных частей**:

1. **Стартовая строка (Start Line):**  
   * *В запросе:* Метод, путь и версия протокола. Пример: `POST /api/students HTTP/1.1`  
   * *В ответе:* Версия протокола, числовой статус-код и пояснение. Пример: `HTTP/1.1 200 OK`
2. **Заголовки (Headers):**  
   Служебные метаданные в формате `Ключ: Значение`. Важнейший заголовок — `Content-Type`. Он указывает, в каком формате передаются данные в теле сообщения. Например, `Content-Type: application/json` говорит о том, что внутри находится JSON.
3. **Тело (Body):**  
   Отделяется от заголовков **пустой строкой**. Содержит сами передаваемые данные (строку, JSON-объект или массив). У простых GET-запросов тела обычно нет.

### 🔬 Практическое мини-задание: «Исследование заголовков»

1. Выполните любой успешный запрос в файле `requests.http`.
2. В нижней панели Rider (вкладка `Services`) найдите окно с результатом ответа, посмотрите на ответ и на запрос через `Show Request`. Найдите у запроса и ответа 3 части: стартовую строку, заголовки, тело.
3. **Проверка на контролируемую ошибку:** Измените в `.http` файле у `POST`-запроса заголовок `Content-Type: application/json` на `Content-Type: text/plain` (простой текст) и отправьте запрос заново.
4. Посмотрите, какой статус-код вернет сервер.

**Ожидаемый результат:**  
Сервер вернет статус-код **`415 Unsupported Media Type`** (Неподдерживаемый тип данных). Так происходит, потому что атрибут `[FromBody]` в ASP.NET Core по умолчанию настроен на работу с JSON. Когда мы принудительно указали `text/plain`, встроенный парсер сервера отказался обрабатывать запрос, защищая приложение от некорректного формата данных.

## ❓ Вопросы для самопроверки

1. Почему роут `/api/get-all-students` — это плохо, а `/api/students` — хорошо? _(Ответ: Маршруты в REST должны быть существительными, действие определяется HTTP-методом GET, а не текстом в URL)._
2. Какие ещё HTTP-методы мы рассмотрели на занятии? Для чего они нужны? _(Ответ: POST — создание ресурса, DELETE — удаление ресурса)._
3. Что произойдет со списком студентов, если убрать ключевое слово `static` у поля `Students`? _(Ответ: Список будет обнуляться при каждом новом запросе)._
4. Из каких частей состоят HTTP-запрос и ответ? _(Ответ: стартовая строка, заголовки, тело)._
5. В каких частях HTTP-запроса передаются параметры при `FromQuery` и `FromBody`? _(Ответ: FromQuery — в стартовой строке URL после знака `?`, FromBody — в теле запроса после заголовков)._
6. Какой статус-код вы вернете, если пользователь пытается войти в профиль, которого не существует? _(Ответ: 404 Not Found)._


> [!CAUTION]
> **Частая ловушка с портами (Localhost):** При запуске проекта ASP.NET Core автоматически назначает случайный порт (например, `localhost:5123` или `localhost:7089`). При копировании примеров запросов всегда проверяйте, чтобы порт в вашем `.http` файле совпадал с портом запущенного в Rider приложения.
